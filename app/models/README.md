# UFriend model integration interface

[English](README.md) | [繁體中文](README.zh-TW.md)

UFriend 0.1.41 supports independent PC APIs and OpenAI-compatible cloud APIs; the desktop app does not download, load or start models. `adapters.cjs` defines the registry, and `main.cjs` registers the LLM, OCR and speech adapters for each source. The corresponding local services are `PC-LLM-API` 0.1.10, `PC-OCR-API` 0.1.0 and `PC-Whisper-API` 0.1.1. Obtain their source code separately and follow each service's README to install it; they are neither subdirectories of this repository nor bundled models. See the [PC model guide](../../docs/guides/PC_MODELS.md) for environments and endpoints.

**Models and compute** in desktop Settings stores the local and cloud connection configurations; each task selects the source it actually uses. `ModelAdapters` registers adapters by source and model kind. `run(kind,{source,task,input,signal,...})` calls only the specified source and does not fall back to the other type. **General** provides the preferred language, while **Personal information** provides model context. See the [model source guide](../../docs/guides/MODEL_SOURCES.md) for usage.

## Implemented integrations and reserved boundaries

| Setting or capability | Current behavior |
| --- | --- |
| `source: 'local'`, `localBackend: 'pc-api'` | `devLlm.endpoint` defaults to port 8765 (mail/polish/chat/translate), `devOcr.endpoint` to 8767 and `devWhisper.endpoint` to 8768, all on `http://127.0.0.1`. |
| `source: 'local'`, `localBackend: 'ugen300'` | No physical device or Hailo SDK is integrated yet; returns `MODEL_NOT_CONFIGURED`. |
| `source: 'cloud'` | `api` stores endpoint, model, ocrModel, transcriptionModel and temperature. The credential store supplies the API Key to the cloud adapter, which supports the OpenAI-compatible protocol. |
| Local OCR and Whisper | The media adapter streams workspace-managed files to the service, polls progress and validates results. Cancellation sends DELETE. |

`status().sources.local/cloud` reports the configuration status of each kind separately; `isConfigured()` does not mean the service is ready. Local **Test connection** calls `GET /health` and checks API v1 and `ready: true`; the cloud check reads `GET /models` to confirm that the specified model is visible. The global `compute` field is migrated only when initializing old data, and the new settings API does not accept it. Old task data without a source is treated as local.

The llm/ocr/whisper entries in `settings.modelDefaults` each store local or cloud. A feature page's temporary selection returns to its default whenever the page opens; changing a default does not cancel a running task. Meeting `recording.source` persists through imports, scheduling, retries and restarts. Each execution fixes request.source, and its controller records both kind and source. Configuration changes cancel only affected running tasks. The locally executed source supplies the result's `meta.source`; a source name returned by a remote service is not trusted.

## PC API calls and data validation

The transport, context-token capacity, service-error rules and timeout values in this section describe the PC services. Desktop task-input and result validation applies to both sources; cloud model capacity depends on the provider and selected model.

If an LLM health response provides `capabilities`, it must be an array of strings containing at least one of `mail`, `polish`, `chat` or `translate`. A service with only OCR/Whisper capabilities will not pass the LLM connection test. Older API v1 services that omit this field remain supported. Both LLM and media JSON responses are checked for valid UTF-8 throughout; malformed bytes produce `MODEL_INVALID_OUTPUT`. If translation or polishing explicitly reports `truncated: true`, `complete: false` or a length-limit finish reason, it produces `MODEL_OUTPUT_LIMIT` and is not saved as a successful result.

The adapter entry point is `run({ task, input, signal, onProgress, onDelta })`. The PC transport normally sends `POST /v1/llm` with JSON `{task, input, prompt?, context?}`. A custom `prompt` contains only `system`/`user`, is stored separately for each task, and defaults to the values from `GET /v1/prompts`. Chat with `onDelta` uses `POST /v1/llm/stream` and parses SSE delta/done/error events; only a completed result conforming to API v1 may be saved. Endpoints permit only loopback HTTP and reject credentials, queries, fragments and HTTP redirects. The services currently bind to IPv4 `127.0.0.1`, so using the default address is the most direct option. Health checks time out after 5 seconds and inference requests after 180 seconds. Ordinary JSON responses are limited to 1 MiB and SSE transfers to 2 MiB.

- `polish`: `input` contains `text`, `use` (`document`/`email`/`message`) and `tone` (`polite`/`casual`/`formal`); returns nonempty `text` and optional `meta`. Before saving, the core validates the text and input version again.
- `chat`: `input.messages` contains only `user`/`assistant` messages from the current chat, beginning and ending with a user message. Limits are 31 messages, 16,000 characters per message and 64,000 characters in total. Actual usable length is also constrained by the 8,192-token context. The service counts tokens exactly, including prompts and a 4,096-token output reserve, and returns 413 if the limit is exceeded without truncating history. Replies are limited to 16,000 characters. Deltas exist only in memory and update one unfinished bubble through separate IPC events. Only completed question/answer pairs are saved; cancellation or failure preserves the question.
- `translate`: `input` contains `text`, `sourceLanguage` and `targetLanguage`. The source may be `auto`; targets are zh-TW/zh-CN/en/ja/ko/es/fr/de. Source text and replies are each limited to 16,000 characters, with an 8,192-token context and a 4,096-token output reserve, also subject to the model's actual capacity. Changes to the source, languages or prompt reject late results from an old task.
- `mail`: each `input.messages` contains exactly one message with `id`, `subject`, `body`, `sender`, `senderEmail`, `date`, `to`/`cc` address arrays and `contentContext`, together with `recipient` and a fixed batch `referenceTime`. `contentContext` contains only availability information such as `attachmentCount`, `unreadImageCount`, `imageTextUnavailable` and `textLimited`. OAuth Tokens, API Keys, BCC, image/attachment files and the entire workspace are not sent.
- For default ordinary `mail`, source lines sent to the model use `[id,field,quoteDepth,text]`, where `field` distinguishes subject from body. Quote depth comes from `>` after 0–3 leading spaces on the original body line; sentence splitting and chunking preserve that source depth. A depth of 0 does not declare whether a line is new or old. Source text and citation IDs are not rewritten. This is the internal input representation in PC 0.1.8 and the desktop cloud adapter; custom templates retain the existing object-based line format.
- `mail-select`/`mail-compose`: internal tasks introduced in PC 0.1.6 and extended in 0.1.7, sharing `{mail:{id,subject,date,sender,to,cc},referenceTime,recipient,lines:[[id,text],...]}`. Select returns `{evidenceIds}`, accepting 0–64 unique IDs that exist among the current candidates. Compose returns `{summary,reason,priority,evidenceIds}`; citations remain limited to 1–8 IDs, and priority accepts only 0/1/2. Internally, the PC selection model decides whether to retain each line, then converts those decisions into an ID array. These tasks use fixed prompts, do not carry custom prompt/context and do not appear in the public Prompt settings. The complete newer workflow requires PC-LLM-API 0.1.7 without downloading the models again.
- A mail response contains one entry in `analyses`, with the same ID as the request. Shared API compatibility validation allows nonempty `summary`/`reason` values of at most 2,000 characters each. Default generated summaries must be under 1,000 characters and reasons under 160 characters. `priority` must be the integer 0, 1 or 2. `evidence` must contain 1–8 nonempty verbatim subject/body excerpts, each at most 1,000 characters. Ordinary PC mail returns at most 4 citations, while chunked merging permits at most 8; all citations must match their sources.
- `mail-classify`: accepts only `input: {summary}`, with a nonempty summary of at most 2,000 characters. It uses a fixed prompt and adds no prompt/context. Returns `{category}`, accepting only the seven IDs work/meeting/finance/account/promotion/personal/other. Missing, invalid or incomplete results cannot be treated as “other.” PC 0.1.5 introduced this capability; if an older service rejects classification, the app displays an upgrade prompt.
- PC 0.1.8 and desktop cloud classification use the same fixed category descriptions and five synthetic counterexamples covering boundaries such as work correspondence, transaction receipts and course marketing. The model judges the whole summary. Program keywords do not assign a category, and neither the original email nor personal context is added to the classification request.
- `meta` may provide service and model information. An allowlist for business results retains `model` and `backend`, with a separately recorded, locally confirmed `source`. Successful long-email results may additionally store `processingMode: 'segmented'` and an integer `chunkCount` from 1 to 128. PC diagnostics separately retain valid request IDs, context, token usage, finish reasons and durations, without saving original request text or full replies.

Stable priority semantics: 0 means the user has an explicit deadline time today or an explicit instruction to act immediately; 1 means the user has a general task today; 2 means no task today or action needed only in the future. Personal responsibility, cancellation and negative conditions should be evaluated before timing. A message being sent today, or the user merely being copied, is not sufficient by itself to determine priority. A topic category, the user being the sender or the absence of request wording also cannot alone change priority to 2. Source citations prove only that a string exists; they do not guarantee a correct summary or semantic classification.

Service error codes include `MODEL_INVALID_REQUEST`, `MODEL_INPUT_TOO_LONG`, `MODEL_REVIEW_REQUIRED`, `MODEL_API_UNAVAILABLE`, `MODEL_API_BUSY`, `MODEL_API_TIMEOUT`, `MODEL_INVALID_OUTPUT` and `MODEL_OUTPUT_LIMIT`. The client also checks `MODEL_API_INCOMPATIBLE` and reports `MODEL_STREAM_INTERRUPTED` if it does not receive a complete stream. Neither output limits nor disconnection permit a partial answer to count as successful. `MODEL_REVIEW_REQUIRED` means the email contains explicit model-control text, inference was not performed and human review is required. This is a conservative rule that may reject legitimate emails discussing such content; it is not complete prompt-injection protection.

## Task lifecycle

LLM requests may include `context: {preferredLanguage?, profile?}`. `preferredLanguage` is used only for chat and is one of zh-TW/zh-CN/en/ja/ko/es/fr/de. Profile is used only for chat, polish and ordinary full-text mail summarization, and contains enabled, nonempty name, phone, personalEmail, workEmail, company, jobTitle and notes fields. The enabled flag stays local; translate and the three internal mail tasks send no context. Profile-field limits, in that order, are 120/80/254/254/120/120/2000 JavaScript characters. The desktop additionally limits JSON-encoded length, and the backend context limit is 5000. Personal context is added as JSON data to the expanded prompt and cannot rewrite the original email recipients, quotations or output validation; its full text is not written to diagnostics.

Settings are validated before being saved and applied atomically. Changing the language cancels only chat; changing effective personal context cancels chat, polish and mail. Identical values or edits to disabled context do not cancel existing tasks. New settings affect only subsequent requests; disabling personal information does not delete it from existing conversations.

`mail.analyze` uses `categorize:true` to process the current inbox one message at a time, including read and done messages. The main button defaults to `onlyChanged:true`; a single-message `ids:[id]` request can use `onlyChanged:false` to recompute everything. The core's existing analysis entry point without categorization remains compatible. A batch stores `processed`/`total`/`failed`/`skipped`/`unchanged`; processed includes successes, failures and skips and cannot be treated as the success count. A running task's phase is summary, chunking, merging or classification. Chunking reports progress through `onProgress(undefined,{stage:'mail-chunks'|'mail-merge',chunkIndex,chunkTotal})`, where chunkIndex is the number of completed chunks. The core accepts only valid progress for the current email's summarization stage and clears it on completion, cancellation or a change of message. An unconfigured model ends the batch early; failure on one message proceeds to the next.

Before sending a summary request to either source, the desktop core uses `splitMailThread(body,{firstOnly:true})` to select the topmost body text. Everything after a recognizable quote or forwarding boundary is excluded from generation, source highlights, quality checks and capacity recovery. Subjects with Re/Fw/Fwd or recognized Chinese reply/forward prefixes are also excluded from the analysis copy. If no text remains, the old subject is not used to invent an event. Ordinary new-message subjects are retained. Image-content status is calculated only for the current HTML region, while attachment status still comes from the original email. Next, `mail-analysis-input.cjs` replaces HTTP(S) and explicit www URLs in the subject/body with `【網址】`; only the reduced text is sent to the adapter, and the mapping to original positions stays on the desktop. Replies are first validated against the reduced input, then quotations are restored and validated again against the selected body. If the same simplified quotation maps to different URLs, shared text excerpts are used only when every occurrence contains a program-generated URL marker and the sequence of contiguous original-text fragments is identical after URLs are removed. Ambiguity involving mixed native and generated markers is still rejected. Unverifiable citations cannot be applied; text on opposite sides of a URL is not joined, and the limits of 1,000 characters per excerpt and 8 excerpts in total still apply. API v1 mail/analyses fields remain compatible. All emails use v9 fingerprints; old v1–v8 summaries are recomputed on the next processing run. Content comparison and fingerprints still use the original email so that different URLs do not cause distinct content to be treated as unchanged.

Both adapters share `mail-processing.cjs`. Each message first receives normal mail summarization into a short topic summary; chunking begins only after `MODEL_INPUT_TOO_LONG`, `MODEL_OUTPUT_LIMIT` or repetitive generation. Each chunk uses mail-select to choose source text, while also retaining a bounded amount of dates, amounts, statuses, conditions and nearby context. If there are too many candidates or the merging input still exceeds capacity, selection is repeated on the candidate source text. Finally, mail-compose generates a unified topic phrase, priority and reason for the current body, restores citation IDs to original text and returns the existing analyses format. Intermediate paragraph summaries are not generated. Each task fixes its source, endpoint, model, key and settings; failure does not switch sources.

Chunking is limited to 128 chunks, 192 internal model calls and 6 reduction rounds. The special workflow has a total time limit of 10 minutes, excluding the first normal summary request, and each individual request remains subject to its own timeout. If chunk selection or merging encounters another input/output capacity limit, verifiable source text may be used to create a result explicitly marked as “Source excerpts,” requiring human review of its priority. This is not a generated summary completed by the model. Cancellation, timeout, malformed output and citation-validation failure still prohibit publishing a result. Both source-text retention and recovery are bounded; complete meaning and successful processing of every long email cannot be guaranteed.

PC 0.1.7 reserves 1,536 output tokens for default mail and mail-compose, with summaries under 1,000 characters and reasons under 160 characters. Mail-select reserves 1,024 tokens and can select 0–64 lines per call; compose cites 1–8 lines. Ordinary mail with a custom Prompt retains the 512-token output contract, and the shared result format remains compatible. Chat/translate each reserve 4,096 tokens; polish/mail-classify each reserve 512. All prompts, fields and output budgets count toward the 8,192-token context.

Through `mail-quality.cjs`, the core stores `analysis.sourceFacts`: at most 32 verbatim excerpts, each at most 1,000 characters. The UI initially shows 3 excerpts and can expand the rest. The model cannot fill in these excerpts, and they do not mean that the summary has received complete semantic validation. The desktop sets `analysis.quality.sourceFactsTruncated` when source-highlight extraction runs out of capacity, prompting the user to read the original email. This flag alone does not invalidate a generated summary or change its priority. `analysis.quality` stores limited quality checks, content availability and `priorityReview`. Summary and reason are checked separately for newly introduced currencies, some numbers/codes/durations, and contradictions involving attachments or explicit conditions. Only a hard conflict in the summary itself replaces the summary; a conflict in the reason only requires priority review. Insufficient detail coverage, differences in citation wording, and failure to repeat signals such as no action required or already received remain diagnostics only; they do not independently replace a summary or require priority review. The field responsible for a conflict is recalculated each time. Existing issues do not escalate a reason error into a summary error; capacity-recovery source excerpts, conservative handling of insufficient text with unread images/attachments, and pending-review states are retained. Any known unread image may produce an `imageTextUnavailable` notice, not just in messages with fewer than 80 characters of text. Attachments additionally produce `attachmentTextUnavailable` to indicate that they have not been read and that only the email text is being processed. The absence of a warning does not establish that a summary is correct.

A valid summary, summaryFingerprint and categoryStatus:pending are saved first. The same final summary is then sent to mail-classify. Even when marked as “Source excerpts,” only that final text is sent, without separately supplying the original email. Success saves category, categoryMeta, fingerprint and categoryStatus:done; failure saves categoryStatus:error/categoryError. A retry can reuse a summary with the same fingerprint. The v9 fingerprint includes original text, sender address, attachment/image-content status, recipient identity, source and effective model/Prompt/personal-context settings, together with the Taipei date. Unchanged messages may be skipped on the same day; processing on the next day recalculates that day's tasks. A batch fixes referenceTime at its start and continues to use the same date across midnight. Keys, read status, labels and manual priorities are excluded from the cache.

Before applying a result, the app confirms that the message remains in the inbox and that its content, date, sender name/address, To/CC, image/attachment status, the user's addresses and effective processing settings have not changed. Model results are saved in `mail.analysis`. A model priority is applied only when the priority is not manual and there is no `quality.priorityReview`. Uncertain results display a pending-review status rather than treating the model's 0/1/2 as confirmed. `prioritySource: 'manual'`, including a manually cleared priority, takes precedence. Existing 0/1/2 values in old data are also migrated to manual priorities.

Task checks exclude recognized “do not reply” clauses and optional reference/customer-support conditions clause by clause, while retaining review evidence if a subsequent clause still assigns work, specifies a deadline or requests a second action. This only blocks model priorities that lack supporting evidence; it does not assign a new priority and still cannot cover every natural-language condition.

`mail-scheduler.cjs` runs once daily according to settings.mailSchedule enabled/HH:mm, persisting mailScheduleState.lastScheduledDate before synchronizing and processing mail. It uses the computer's local date, defers while busy and catches up only for the current day when resumed. Failures do not cause unlimited retries on the same day. An automatic task captures the default llm source at startup and is mutually exclusive with manual processing. Test mode does not start the timer.

Cancellation must use `signal` to abort the actual HTTP/inference work, rather than merely stopping an onscreen timer. The core also prevents an adapter that ignores cancellation from overwriting data with a late result. Actual connection-configuration changes cancel only work using the same source and affected model kind. Changing polishing text, purpose or tone clears old output; unchanged autosaves do not cancel tasks. On app restart, an unfinished mail batch from the previous session is marked interrupted while earlier results are preserved.

Model output is only data: it cannot trigger sending or deleting email, changing Gmail labels, creating calendar events or executing programs. There is no automatic cloud upload or fallback after failure. Service-side format validation, source citations and polishing checks for numbers/placeholders are safeguards; they do not replace reviewing summaries, amounts, names and negation.

## OCR and Whisper job APIs

`local-media-api.cjs` calls each service's `GET /health` and checks API v1, ready, model/backend and the relevant capabilities. `POST /v1/jobs` sends raw file bytes with `X-UFriend-Client: 1`; it does not send a path or the entire workspace. HTTP 202 returns `jobId`, which is queried with `GET /v1/jobs/{id}` and cancelled with `DELETE /v1/jobs/{id}`.

States are queued/running/completed/failed/cancelled, with progress from 0 to 1. The desktop displays at most 99% until it completes validation. Whisper additionally returns processedSeconds/durationSeconds; a failure on a long recording preserves the processed range but does not apply a complete transcript.

- OCR accepts PNG/JPEG with a 40 MiB limit. The result is `{text, regions: [{text, confidence, box}], meta}`, with each box containing four `[x,y]` pairs. Empty text and empty regions are a valid result when no text is present. The service limits images to 60 million pixels and 20,000 pixels on either side; the app converts imported images to PNG first.
- Whisper accepts raw audio/video bytes up to 1000 MiB, with `X-UFriend-Language` and a URL-encoded basename. The result is `{segments: [{start,end,text}], language, duration, meta}`. Times must not be negative, reversed or exceed the file duration; empty segments mean no speech.
- Media responses are limited to 12 MiB. Timeouts are 5 seconds for health checks, 30 seconds for an individual request, 10 minutes for uploads, and a total processing limit of 180 seconds for OCR or 2 hours for Whisper. Cancellation cleanup uses a separate 5-second request. Timeouts, busy services, malformed output and services that are not ready use safe messages without exposing internal service paths.
- Changing an endpoint cancels only the corresponding capability. Replacing an image, editing text, deleting a recording or changing its language prevents late results from overwriting the new state. Exiting the app cancels running model tasks and waits for bounded cleanup.

## Cloud APIs

`cloud-api.cjs` registers three adapters by kind. Each task first fixes the endpoint, model, key and parameters in effect at that time. Redirects are forbidden, and raw provider error bodies are neither displayed nor written to diagnostics. LLM and OCR use Chat Completions with `store: false`. Public text tasks retain custom prompts and existing result validation; mail chunk selection, merging and classification use fixed prompts without personal context. Long emails use the same shared workflow, while actual capacity still depends on the provider and model. Chat results can be saved only after a successful finish reason and the complete `[DONE]` marker are received.

OCR sends PNG, JPEG or WebP images up to 20 MiB and does not invent coordinates. `cloud-audio.cjs` uses local FFmpeg to extract mono 16 kHz MP3 audio and merges timestamps using the actual starting positions from the segment list. Each segment is smaller than 25 MB, and total length is limited to 12 hours. Transcriptions must provide `verbose_json`, duration and segments; missing timestamps produce an incompatibility error rather than estimated subtitles.

Success, failure and cancellation all wait for temporary audio cleanup. Cleanup results are checked again when exiting; if this task's temporary files still cannot be removed, the app remains open and displays an error. See the [model source guide](../../docs/guides/MODEL_SOURCES.md) for API fields, compatibility requirements and the scope of transmitted data.

## Future UGen300 integration

The preferred approach is to retain API v1 and replace the PC llama.cpp backend inside an independent local service with a verified UGen300/Hailo backend. Desktop UI, storage formats, progress and cancellation boundaries can be reused. A future product must still explicitly provide a proper device-mode integration; the current “PC test API” label cannot be presented as an existing hardware integration. The hardware service manages model loading, HEF compatibility, device IDs, disconnection and resource release. PC GGUF files are not directly portable HEF files.

1. After integrating one model capability, use fixed data to verify quality and cancellation/failure behavior before extending other capabilities.
2. OCR is one logical worker covering text detection, crop ordering, recognition and merging. It may manage two networks and need not consist of a single model file.
3. Whisper audio extraction and format preprocessing stay inside the independent service. The desktop adapter sends raw audio/video bytes and receives segments with start/end times; progress comes from the audio already processed by the service or backend events. Future hardware services should keep the same boundary rather than maintaining a second preprocessing workflow on the desktop.
4. `services/model-pool.cjs` is currently an explicit simulation of timed scheduling. Physical-device integration must replace timer assumptions with SDK completion/failure events and actual resource lifecycles; simulated completion does not mean a model has finished.

UGen300 integration still requires checking model, HEF and runtime compatibility against the vendor SDK. Quantization, speed, power consumption and USB behavior must be validated separately for PC and UGen300.
